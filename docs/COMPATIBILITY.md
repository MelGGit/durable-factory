## Offline evidence

- Configuration persists through a service restart in real SQLite. Revision checks reject stale saves atomically.
- A newer application schema blocks readiness and writes; the stored configuration is not replaced.
- Exclusive storage ownership blocks a second service and recovers immediately after abrupt process death. A 15-second stalled-owner regression verifies that elapsed time cannot authorize takeover by a second process.
- A committed partial model response survives process death as interrupted history; the accepted input and queued follow-up finish after reopening the same storage. Retrying the request ID returns the original submission.
- A read-only tool declared replay-safe runs again after restart and produces one committed tool result.
- An unsafe fixture writes an observable effect, emits committed partial output, and is killed before result commit. Recovery does not execute it again; the transcript contains an interrupted tool result and retained output. Workflow adapters must interpret that outcome before future real mutations; stage 5 models that reconciliation with deterministic adapters.
- Credential modifications serialize read-modify-write and preserve concurrent token rotations. Offline tests exercise Pi's automatic refresh of expired OpenAI and Anthropic credentials, failure preservation, and saving rotated credentials after caller cancellation. Damaged credentials surface per-connection errors without preventing settings saves or token replacement/removal. API responses omit secrets. Host/origin/CSRF boundaries and configuration validation are exercised.

## Known boundaries

- Pi Durable's SQLite backend uses WAL with `synchronous=NORMAL`: process-crash recovery is not a guarantee against power loss. Do not copy just a live database file while ignoring WAL state.
- Pi does not provide cross-process ownership locking. The application holds an exclusive OS file lock using an empty SQLite lock file, separate from application storage and storing no workflow state. It has no heartbeat expiry: a live stalled owner cannot be replaced, and a dead owner releases its lock automatically. Legacy heartbeat-lock directories block startup until the older service is stopped and any leftover legacy directory is explicitly cleaned up. Never replace the new mutex files while a process may hold them.
- Subscription credentials are stored only under their selected provider. Ambient environment credentials and CLI logins are not used. Provider-owned refresh runs inside the credential-store lock.
- Requesty is registered as a custom OpenAI Chat Completions provider at `https://router.requesty.ai/v1`. Conservative fallback model limits are 8192 context / 1024 output tokens; catalog capacity, reasoning, price and account access are not inferred. No cost estimates are displayed.
- Credentials now use macOS Keychain or Linux Secret Service through the pinned native vault binding. Legacy private files migrate only after verified vault storage; no plaintext fallback is allowed. Tests inject disposable fake vaults and never enumerate personal credentials. Native store availability depends on the local desktop/session and is covered by an opt-in fake-entry smoke test.
- The application exposes local `/api/v1` planning chat plus real and simulation workflow adapters. Real execution activates when configuration is complete; simulation and disabled overrides remain available. Subscription authentication UI and backup/restore remain later work. Simulation conversations never call a coding/review model or run a repository command.

## Stage 4 planning and GitHub evidence

- Real Pi documents store repository identities, ticket revisions, proposals, authorizing submissions, and immutable issue operations alongside existing chat state. Upgrading earlier conversations preserves history and model choices. Older records without a captured base branch use `main`; they never adopt a later settings change implicitly.
- Deterministic planner tools save and propose a ticket. Service checks reject missing, stale, ambiguous, negative, queued, or withdrawn approval. Repeated sends and concurrent tool calls create one issue operation. Changed tickets and non-affirmative replies invalidate pending proposals.
- Fake GitHub covers successful creation, definitive rejection, lost response, uncertain outcome, multiple reconciliation pages, ignored pull requests, duplicate markers, token rotation, expired tokens, denied access, rate limits, invalid responses, and server failures. Read-only validation explicitly leaves write access unverified.
- The issue recovery worker persists a simulated remote issue, then is killed before returning its identity. Restart recovers the same operation and approving submission, records issue 42, and observes exactly one external POST. No account-backed GitHub writes or paid model calls are used.
- Repository tests cover current uncommitted files, tracked edits/deletions, ignored tracked/untracked files, symlink escape, traversal, binary and large-file limits, configured clean/process filters that must never execute, and a redirected `core.worktree` that must not expose files outside the registered root. History search is conversation scoped and bounded.
- Browser verification exercises proposal display, affirmative chat approval, an uncertain result, reconciliation, restart, the restored issue link, repository validation, and desktop/mobile rendering. The ticket panel scrolls independently and leaves the mobile composer accessible.
- Reconciliation scans at most 100 pages per attempt. If a write might have succeeded but no marker is found, the operation remains uncertain instead of issuing another POST. Multiple matching issue identities block creation. GitHub.com is the only supported host in this stage; real account capability is not claimed by the offline suite.

## Review fixes

- Git inspection pins its worktree explicitly, so repository-local `core.worktree` cannot redirect reads to a sibling directory. A disposable-repository regression verifies listing, reading, and diff output stay in the registered root without rewriting Git configuration.
- Planning cancellation reaches GitHub lookup and request dispatch. An interrupted lookup cannot start a POST, including after restarting the service; an explicit retry reuses the original operation. Tests also verify cancellation while credentials resolve sends nothing, aborting an in-flight POST leaves an uncertain outcome, and confirmed or reconciled results from already-issued writes preserve one linked issue without another POST.

## Stage 5 workflow evidence

- Durable Pi tasks and documents implement a FIFO serial queue and setup/baseline/developer/check/reviewer/publication stages. Concurrent manual/chat starts converge on repository/issue identity; ordinary retries return completed work and only an explicit new-run request admits another run.
- Scripted adapters cover successful output, check failure, reviewer rejection, invalid review, questions, provider failure, repair exhaustion and recorded continuation. Three repairs are counted at repair start. Guidance and specification/configuration adoption preserve accounting, including setup adoption while an outstanding repair remains capped.
- Captured settings do not follow later saves. Explicit adoption invalidates evidence; setup changes repeat setup/baseline. Evidence includes source/configuration/specification identity, check commands, exit status, duration and review verdict. Changed source/base identity forces validation again; mismatching publication content never reaches readiness through reconciliation.
- Developer input uses the durable chat submission interface, is delivered only at a boundary and can be withdrawn before consumption. Guidance during failed checks still consumes its normal repair; publication closes new implementation input and reviewers reject ordinary chat.
- Stored answers reject stale/conflicting updates and deduplicate operation retries. Pause/cancel propagate to adapter work. Deterministic clocks exercise provider deadlines and bounded cancellation; late results cannot advance interrupted attempts. Unconfirmed termination retains the slot, while confirmed release allows queued/resumed work to acquire it serially.
- Five workflow SIGKILL scenarios cover validation, repair, human-question wait, simulated remote publication effects and cancellation after a stage task stops. Recovery retains attempt/task identity and repair count, increments recovery count, restores questions and reconciles the existing publication effect without repeating it. Late confirmed effects remain recorded after cancellation.
- Browser checks cover labelled starts, activity inspection, desktop/mobile question restoration after restart, answers, pause/resume/cancel, queued guidance/withdrawal, stream reconnection and reviewer transcript links. Screenshots in `test-results/workflow-*.png` are visually inspected. The inspector’s labels make clear that simulated PR readiness creates no GitHub PR.
- Type checks, formatting checks, production build, the offline suite and the browser suite pass. Those stage 5 results established simulated orchestration; the additional real-adapter evidence below covers stages 6–7 without claiming live account access.

## Stage 5 review regressions

- Adopting configuration or specification while setup/baseline is paused preserves those prerequisites. Scheduler admission also prevents developer work while setup remains required.
- Chat interruption cannot weaken an in-progress cancellation or its termination blocker. Recovery preserves the cancelled stop target when a task ended before the run’s cancellation outcome committed.
- Paused and shutdown publication operations can reconcile a confirmed effect or confirmed absence without resuming automatically. Confirmation clears uncertainty, and explicit resume reuses the same publication operation; termination reconciliation does not recreate resolved uncertainty.
- Targeted regressions cover all three review findings, including a browser pause → reconcile → explicit resume flow and a forced crash during cancellation. The complete offline and browser suites pass with the counts above.

## Stages 6–7 real-adapter evidence

- Real Pi conversations call scoped read/write/edit/command tools in isolated worktrees. Fresh reviewers inspect the exact candidate tree, including explicitly included ignored generated files. Candidate file reads are paginated and stream blobs beyond the ordinary command output limit. Deleted ignored selections remain valid candidate deletions. The developer has no publication tool; the reviewer has no mutation or unrestricted shell tool. Missing structured verdicts block publication.
- Setup/baseline failures pause before development. Real check evidence retains commands, actual exit codes, duration, source/configuration/specification identity, and complete paginated UTF-8 output. A regression reconstructs 80 KiB of multi-byte output without replacement characters or arbitrary path access.
- Supervised launch persists intent and supervisor PID/start identity before authorization. Deadlines terminate process groups and account for ordinary detached children. Shutdown/disconnect terminates the owned group before losing the supervisor identity; zombies are distinguished from live mutation-capable processes. Unknown/failed inspection retains the slot. This is not an OS sandbox against deliberately evasive commands.
- SIGKILL workers cover developer commands, commits with active hooks, pushes with active receive hooks, and remotely created PRs before acknowledgement. Recovery preserves attempts/repairs/worktrees, blocks incompatible simulation-mode execution, records existing effects, and requires explicit inspection before continuation. Interrupted commands do not replay automatically. Commit and push reconciliation avoid duplicating their existing effects.
- Content changes during review force development and fresh validation. Ignored disposable output does not invalidate intended source. Base movement integrates before publication and repeats checks/review without consuming a failure repair. Hook-generated content blocks push until explicit service-only revalidation, with implementation input still closed.
- Lost PR responses reconcile one marked PR across open/closed inspection without another creation. PR readiness verifies both source and target repository/branch identities as well as the head SHA. Startup label/manual races converge on one run; persistent labels cannot restart finished work. Label admission is fenced against configuration changes while a poll is pending. GitHub endpoint tests cover issue snapshots, encoded branch queries, non-draft creation, and rate-limit backoff.
- The private Git helper is tested through Git's real credential protocol, without a network request. It resets ambient helpers, scopes credentials to the selected GitHub repository, and keeps the token out of its environment and helper source. Publication transport is exercised against disposable local bare remotes; HTTPS/GitHub adapters use mocked responses. No paid model calls or live GitHub writes are part of verification.
- Interrupted admission and graceful shutdown during issue lookup create no run after cancellation/closure. Captured Requesty model registrations are restored before workflow reconciliation.
- Observed on macOS with Node 24.18.0. Linux uses the POSIX process-inspection path but was not exercised in this environment. Submodules and deliberate supervision evasion require manual handling or a stronger execution environment. The stage 8 results below add merged-run cleanup; backup/restore is deferred.

## Stage 8 review regressions

- Ignored Git files are not assumed disposable solely because they are ignored. Before the first push, publication saves a content/path/type/mode fingerprint and file count without storing their contents. Cleanup recomputes the fingerprint without following symlinks or running filters. New or changed ignored files block deletion; unchanged captured output can be removed. Older runs without a fingerprint retain ignored files until the user preserves or removes them.
- A real required-check fixture creates ignored cache output before publication. Regression tests add a new ignored notes file, then modify the captured cache file: both remain intact and block cleanup despite a clean ordinary Git status. Restoring the baseline allows cleanup to finish. A legacy-run regression verifies that the current ignored-file state is never silently adopted as its baseline.
- Failed storage reopening now retries up to three times with short backoff while readiness is blocked. Each failed partial initialization closes its new workflow/chat/harness before retrying; an uncertain close stops recovery rather than admitting a second writer. The readiness/API error explains automatic retry or the required restart, never the underlying private exception. Successful recovery clears the error; shutdown cancels retry timers.
- A temporary data-directory permission failure reproduces the reviewed outage and now recovers automatically after access is restored. A failure injected after opening the new harness verifies three bounded attempts, closure of partial instances, redacted recovery messages, and clean shutdown. The focused cleanup/recovery suite passes all 13 tests, including the existing forced termination and deletion checks. The complete offline suite passes all 116 tests, all 12 browser tests pass, and type checks, formatting verification and the production build pass.
